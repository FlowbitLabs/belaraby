# Belaraby — Claude Context

Arabic learning platform: Flutter app (iOS/Android/web) + React admin dashboard + Supabase backend. Arabic-only UI.

```
frontend/   Flutter app (iOS, Android & web)
dashboard/  React admin panel (Vite + React Admin + MUI)
supabase/   Migrations, config, seed data
```

---

## Flutter (`frontend/`)

### Architecture
- Feature folders under `lib/app/` — each has `cubit/`, `view/`, `widgets/`
- Data layer under `lib/data/` — `models/`, `repositories/`, `services/`, `supabase_client.dart`
- Global Supabase client: `lib/data/supabase_client.dart` — use `supabase` directly, never instantiate a new client

### State Management (Cubit/BLoC)
- Use `Cubit` for simple state, `Bloc` for event-driven flows
- States extend `Equatable` and implement `copyWith`
- State has a `status` enum: `initial | loading | success | error`
- Cubits call repositories — never call Supabase directly from a cubit
- UI emits events / calls cubit methods — no business logic in widgets
- Use `BlocBuilder` to rebuild UI on state, `BlocListener` for side effects (snackbars, navigation)

```dart
// State pattern
class FooState extends Equatable {
  const FooState({this.status = FooStatus.initial, ...});
  final FooStatus status;

  @override
  List<Object?> get props => [status, ...];

  FooState copyWith({FooStatus? status, ...}) => FooState(status: status ?? this.status, ...);
}
```

### Data Layer
- Repository pattern: one repository per domain (e.g. `LessonRepository`)
- Use `.withConverter()` on Supabase queries for type-safe mapping
- Models have a `factory fromJson(Map<String, dynamic>)` constructor
- Models do NOT extend Equatable — that's for states/events only

```dart
// Query pattern
supabase.from('lessons').select().withConverter((data) => data.map(Lesson.fromJson).toList());
```

### Widgets & Style
- `StatelessWidget` by default; `const` constructors everywhere possible
- `final` for all fields
- Break large widgets into smaller named widgets — avoid anonymous builders for complex UI
- Use `easy_localization` for every user-facing string — no hardcoded strings
  - Translation keys live in `assets/translations/`

### Error Handling
- Cubits catch exceptions and emit error state
- UI uses `BlocListener` to show snackbars/dialogs on error status
- Never swallow exceptions silently

### Quality
- Run `flutter analyze` before committing — project uses Very Good Analysis
- Fix all warnings, not just errors

## Dashboard (`dashboard/`)

### Stack
React 19 · TypeScript · Vite · React Admin 5 · ra-supabase · MUI v7

### React Admin Patterns
- Define resources with explicit `<Resource>` components — never use `AdminGuesser` in production
- Use `<List>`, `<Datagrid>`, `<Edit>`, `<Create>`, `<SimpleForm>` before writing custom pages
- `useNotify` for user feedback, `useRecordContext` to access the current record
- `useDataProvider` for custom data calls that fall outside CRUD

```tsx
// Resource pattern
<Resource name="lessons" list={LessonList} edit={LessonEdit} create={LessonCreate} />
```

### TypeScript
- Strict mode — no `any`, no implicit `any`
- Define interfaces for all props, state, and API responses
- Named exports for all components

### Auth
- Uses `supabaseAuthProvider` from `ra-supabase`
- The Supabase key must be the anon JWT (`eyJ...`) — not the `sb_publishable_` format
- Admin users must be created manually in Supabase Auth → Users

### Running
```bash
cd dashboard && npm run dev
# or: VS Code → Run & Debug → "dashboard"
```

## Supabase

### Migrations
- One file per change in `supabase/migrations/` — never edit existing migration files
- Name format: `<timestamp>_<description>.sql` (generated by `supabase migration new <name>`)
- Write idempotent SQL: use `IF NOT EXISTS`, `IF EXISTS`, `OR REPLACE`
- Always include a rollback comment at the top of destructive migrations

### Row Level Security
- RLS must be enabled on every table
- Define explicit policies for each operation (SELECT, INSERT, UPDATE, DELETE)
- Use `auth.uid()` to scope user data; use `auth.role() = 'authenticated'` to gate writes
- Prefer restrictive defaults: deny all, then add allow policies

```sql
-- RLS pattern
ALTER TABLE lessons ENABLE ROW LEVEL SECURITY;
CREATE POLICY "public can read lessons" ON lessons FOR SELECT USING (true);
CREATE POLICY "owner can update" ON lessons FOR UPDATE USING (auth.uid() = user_id);
```

### Local Dev
```bash
supabase start          # start local stack (requires Docker)
supabase db reset       # re-apply all migrations + seed
supabase db push        # push migrations to production
supabase migration new <name>  # create a new migration
```

- Studio: `http://localhost:54323`
- API: `http://localhost:54321`

## General Rules

- Check `pubspec.yaml` / `package.json` before suggesting new packages — prefer what's already installed
- Never commit `.env` files or Supabase service role keys
- `main` is the only long-lived branch; pushing to it deploys production. Keep Flutter, dashboard, and Supabase changes in separate commits
- Keep Flutter, dashboard, and DB types in sync — if a column changes, update the Dart model and TS interface
